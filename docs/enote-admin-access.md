# ENOTE-LABS 관리자 입장

2026-11-02. 대표가 확인한 이메일을 최초 대표 슬롯으로 예약했다. 서버의 실제 Auth 사용자와 이메일 확인 상태, 유효한 Auth 세션을 확인한 뒤에만 해당 슬롯을 사용할 수 있다. 계정을 임의 생성하거나 이메일을 대신 인증하지 않는다. 대표의 첫 올바른 관리자 비밀번호 입력 때 Auth 사용자 ID에 바인딩한다.

## 동작

- `/admin/`: 최초 제품 계정 로그인 → 서버 역할 확인 → 별도 관리자 비밀번호 확인 → 4개 제품 바로가기.
- 대표만 이메일 확인을 마친 기존 제품 회원에게 운영 관리자 역할을 부여·해제할 수 있다. 지정 관리자에게 재위임 권한은 없다.
- 원문 비밀번호와 해시는 공개 코드에 넣지 않았다. 해시는 로컬 bcrypt cost 12로 계산한 뒤 비공개 설정에 별도로 저장했다.
- 권한 확인에는 사용자 편집 가능한 metadata를 사용하지 않는다. 모든 관리 요청에서 역할·이메일 확인·Auth 세션·비밀번호를 다시 확인한다.
- 5회 실패 시 15분 잠금. 실패 횟수는 예외로 롤백하지 않고 오류 객체를 반환해 보존한다.
- 브라우저는 비밀번호를 저장소에 보관하지 않고 메모리 참조만 사용한다. 화면 잠금·언마운트·15분 경과 시 비운다. 이 15분 UI 잠금은 별도 Auth 세션 생성 또는 회사 자료 권한의 의미가 아니다.
- 운영 관리자 역할은 기존 회사 RLS/구성원 권한을 우회하지 않는다. 고객 회사 자료의 일괄 조회, 회사 관리자 승격, 이메일 확인 우회 기능을 추가하지 않았다.
- `enote_private` 4개 테이블은 직접 API로 노출하지 않으며 직접 테이블 접근을 회수했다. private definer + auth 검증과 public invoker 래퍼만 사용한다.
- security advisor INFO 4건은 해당 비공개 테이블의 RLS에 정책이 없는 의도된 기본 거부 상태다. 이를 해소하려고 광범위한 허용 정책을 넣지 않는다.

## 같은 도메인의 제품 연결

`/flownote/` 빌드를 별도 하위 출력 디렉터리에 생성한다. `/flownote/account.html`과 React 제품은 동일 origin에서 인증 저장소 키를 공유한다. 기존 독립 Flownote 호스트의 세션 설정은 유지한다. 새 가입은 이미 허용된 독립 Flownote 인증 반환 주소를 사용하며, 사용자가 이메일 확인 후 ENOTE-LABS에서 최초 로그인해야 한다. 인증 반환 허용 목록을 넓히지 않았다.

## 검증과 한계

`scripts/verify-admin-transaction.sql`이 운영 DB에서 합성 계정/세션과 테스트 전용 암호를 이용해 실행된 뒤 전체 롤백됐다. 비권한자·위조 metadata 거부, 확인 안 된 이메일 거부, 실제 세션 존재 확인, 실패 횟수와 잠금, 대표의 지정·해제, 지정 관리자의 위임 금지, 즉시 권한 회수, 익명 실행 및 설정 테이블 접근 거부, authenticated invoker 래퍼를 통과했다. 테스트 계정 잔존 수는 0이다.

실제 대표 계정의 가입·이메일 수신·관리자 브라우저 입장은 아직 미검증이다. SMTP 설정 활성화와 Gmail 호스트는 확인했지만 이것만으로 이메일 전달 성공을 증명하지 않는다. 확인 없이 ‘전체 인증 완료’로 보고하지 않는다. 회사별 데이터 권한은 기존 통합 검증 범위를 유지한다.
