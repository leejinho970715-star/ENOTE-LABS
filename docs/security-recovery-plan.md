# 보안·개인정보·복구 운영 대책 (2026-11-03)

## 현재 판정

- 4개 제품은 무료 데모이며 제작 의뢰만 별도 견적·계약으로 비용이 발생한다. 실제 고객·직원의 개인정보, 민감한 계약·계좌·급여 자료를 받는 상용 운영은 별도 출시 조건을 확인한다.
- Supabase 대시보드에서 **FREE** 확인. 기본 유출 비밀번호 검사는 Pro 이상이다. 요금제는 변경하지 않았다. 따라서 Supabase `auth_leaked_password_protection` 경고는 남는다.
- 새 아이디 가입 Edge Function에 Pwned Passwords range 검사를 추가한다. 원문·전체 해시·이름·아이디·이용자 IP를 검사 API로 보내지 않고 SHA-1 앞 5자리만 서버에서 조회한다. 응답 패딩을 요청하며 입력 도중 조회하지 않는다. 유출 확인 또는 검사 장애 시 Auth 계정을 만들지 않는다. SHA-1은 외부 목록 비교용이며 비밀번호 저장 방식으로 사용하지 않는다.
- 이 검사는 **새 아이디 가입 경로만** 대상으로 한다. 기존 비밀번호, 기존 이메일 가입/재설정, 다른 관리자 API·직접 Auth 비밀번호 변경 전체를 보호한다고 표시하지 않는다. Supabase native 검사 활성화 또는 Auth hook 등 전체 경로 통제는 후속 과제다.
- 운영 Auth의 `Require current password when updating`을 켜고 저장 후 재열람하여 1임을 확인했다. 사용자 비밀번호를 대신 변경하지 않았다. 아이디 계정의 존재하지 않는 내부 이메일로 nonce를 보내는 변경 방식은 활성화하지 않았다.
- 비밀번호 검사, 가상 인사·거래, 복구 파일 대조는 자동시험으로 검증한다. 운영 DB 복원·첨부파일 전량 복원·장애 시점 복구가 완료됐다는 뜻이 아니다.

## DB와 첨부파일을 나누는 복구 계획

**제안 목표이며 아직 달성 실적이 아니다:** 실고객 운영 전에 매일 백업(잠정 RPO 24시간), 분리 환경 1영업일 이내 복구(잠정 RTO), 7일 순환 보관을 원가·고객 계약·삭제 정책과 함께 확정한다. 유료 인프라 선택은 CEO가 비용을 확인한 뒤 결정한다. 운영 계정으로 접근할 수 있는 동일 프로젝트 한 곳에만 백업을 두지 않는다.

### 1. 확보

- 실제 요금제의 DB 백업·다운로드·복원 가능 범위를 확인한다. 무료 요금제 자동 백업을 전제로 하지 않는다.
- 운영 PostgreSQL 17과 호환되는 도구로 승인된 DB dump를 만든다. 업무 스키마뿐 아니라 Auth·Storage 메타데이터·확장·역할·RLS·함수·회사 연결 및 private 관리자 설정의 복구 범위를 별도로 기록한다. Auth 해시가 포함될 수 있으므로 암호화·접근 제한·키 분리·보관 만료를 적용한다.
- 비공개 Storage의 **원본 파일**을 별도로 내려받고 bucket/object 이름·크기·해시·콘텐츠 유형·회사 소속을 대조한다. DB 덤프에는 파일 본문이 없으므로 빈 버킷도 ‘객체 0개’ 목록을 남긴다.
- DB/Storage 원본 파일의 시점이 달라지지 않도록 제한된 점검 창 또는 일관된 스냅샷·업로드 예약 처리 방식을 정한다. 범위를 줄인 테이블 CSV를 전체 DB 백업이라고 부르지 않는다.
- 저장 전·후 암호화를 확인하고 키는 별도 비밀 저장소로 관리한다. `backups/`, `*.dump`, `*.backup`은 Git 제외 대상이다. `.gitignore`가 암호화나 접근 통제를 대신하지 않는다.

### 2. 무결성 도구

운영 자료를 공개 저장소나 `dist/`, `public/`에 놓지 않는다. 아래 폴더는 이미 적법하게 확보한 자료를 보안 저장소 안에서 준비하는 형식이다.

```
backups/staging/database.dump
backups/staging/storage-catalog.json
backups/staging/objects/<bucket>/<안전한 파일 경로>
```

`storage-catalog.json`은 `[{"path":"objects/bucket/file.png","bytes":123}]` 배열이다. 실제 object 이름과 안전한 로컬 경로의 매핑·콘텐츠 유형·회사 소속은 별도 보호된 운영 기록에 보관한다. 객체가 없으면 `[]`를 남긴다.

```
node scripts/recovery-manifest.mjs create backups/staging backups/manifest.json
node scripts/recovery-manifest.mjs verify backups/restored-files backups/manifest.json
```

도구는 파일별 SHA-256·크기·누락·추가 파일·카탈로그 일치를 확인하고 심볼릭 링크와 기존 manifest 덮어쓰기를 거부한다. `database.dump`의 PGDMP 헤더 검사는 형식 확인에 불과하다. **PostgreSQL 복원·쿼리 검증이 아니다.** 테스트의 dump는 고의로 가짜 헤더 fixture이며, 실제 dump 복구 실적으로 보고하지 않는다. manifest도 변조되지 않도록 원본 백업과 별도 보호한다.

### 3. 복원 훈련

- 운영 프로젝트에 복원하지 않는다. 승인된 로컬 PostgreSQL/Supabase 또는 별도 비운영 프로젝트와 새 비공개 버킷을 사용한다. 유료 프로젝트 생성은 비용 승인 후 진행한다.
- 비운영 환경에서는 메일·외부 알림·실제 결제·자동 작업을 막고 운영 인증정보를 재사용하지 않는다.
- DB를 복원하고 Auth·RLS·함수·역할·핵심 테이블 건수·회사 연결·최신 승인 버전을 대조한다. 기존 세션·인증정보 재설정 범위도 정한다.
- Storage 원본을 비공개로 복원하고 object 이름·크기·SHA-256과 권한 있는 다운로드, 타 회사·익명 접근 거부를 확인한다. DB에 파일 이름이 존재하는 것만으로 복구 성공 처리하지 않는다.
- 신규 비운영 세션으로 회사별 접근, 독립 검수, 승인본 출력, 매핑된 작업 상태를 확인한다. 실제 고객에게 파일·메일을 발송하지 않는다.
- 시작/종료 시각·누락·오류·복구된 기준 시점·실측 RPO/RTO와 검증 결과를 남긴 뒤 검증 계정·복원 사본의 보관·파기 기한을 적용한다. 고객 자료 사본 삭제는 권한과 보존 의무를 확인한 운영 절차로 수행한다.

### 현재 막힌 실제 검증

이 작업 환경에는 `pg_dump`, `pg_restore`, `psql`, Docker가 없고 승인된 별도 복구 DB 연결도 없다. 따라서 파일 무결성 테스트와 기존 로컬 SQLite 백업 시험은 수행 가능하지만, 운영 PostgreSQL·Storage 통합 복구는 **미검증**이다. 운영용 비밀번호를 채팅에 받거나 공개 파일로 저장하지 않는다.
